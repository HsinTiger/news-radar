## 2. 關鍵實作決策

### 2.1 jsonl + lineage atomic 對齊
spec 寫 "single logical commit, your call"。選擇：jsonl append 先（捕捉
pre_size），lineage INSERT 後；lineage 失敗就 truncate jsonl 回 pre_size。
這個方向勝過反過來（lineage 先、jsonl 後）的理由：jsonl 是 canonical
record（roadmap §1.3），先確保它落盤；如果 sqlite 暫時不可用我們至少
還可以從 jsonl 重建 lineage，反過來不行。

### 2.2 update_decision 的 jsonl 改寫策略
不做 in-place line edit（line 長度可變、會位移後續 bytes）。改用 tmp
file + `os.replace`（POSIX atomic）整檔重寫。週檔 bounded（一週幾十
proposals 量級），重寫成本低。

### 2.3 schema.sql vs migration file
兩個都寫 — schema.sql §9 inline CREATE TABLE/INDEX（給 fresh DB），
migration sql file 給 production DB 增量遷移用。`_migrate_proposal_lineage`
重跑 migration sql；statements 全部 `IF NOT EXISTS` 所以重跑零成本。
這個 dual-write 保持 schema.sql 是 single source of truth、同時又有
migrations/ 的 dated audit trail（跟 2026-04-25 log-scale migration 一致）。

### 2.4 不用 schema 驗證套件
hand-rolled `validate_proposal()`。理由：proposals 是 internal API，
ENUM 集合穩定（5 analyzers、4 platforms、5 proposal_types），加
jsonschema/pydantic 對這個 surface 來說是過度工程。validation 失敗
直接 raise `ProposalValidationError`，呼叫端 catch 後 log 即可。

### 2.5 ISO-week 計算
`datetime.isocalendar()` 給 (year, week, weekday)。2026-04-27（Mon）
是 W18 不是 W17（Hsin 要注意這點：spec 寫 "YYYY-WW.jsonl" 但日期到
週數的對應要用 ISO 標準）。test fixtures 全部用真實日期。

### 2.6 state-branch 推送
**刻意 defer**。spec red-line #5 也明講 — proposals.py 不該有 state-branch
push 邏輯，那是 Items 4+ 從 cron 寫入時要決定的事。audit 有記。
