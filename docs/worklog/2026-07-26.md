## What landed

### 1. `26bb82d` — relax `python-dotenv` pin

- `requirements.txt`: `python-dotenv==1.0.1` → `>=1.2.1,<2.0.0`.
- Reason: `python-substack` 0.1.21+ requires `python-dotenv>=1.2.1`; the
  dead pin makes pip resolution fail with `ResolutionImpossible`.

### 2. `7843dde` — "記住此裝置" (remember this device) opt-in

Owner token was `sessionStorage`-only, so mobile Safari background
reclaim / PWA relaunch / tab close all forced a re-paste.

- `substack-submit/index.html` — added `#remember-device` checkbox;
  `token()` now reads `localStorage` first then `sessionStorage`; new
  `storeToken(value, remember)` writes to exactly one store (clearing
  the other first) and `clearToken()` clears both. Lock button and
  auth-failure path use `clearToken()`. On load, an existing
  `localStorage` token pre-checks the box.
- `dashboard/index.html` + `dashboard/app.js` — same treatment; the
  input+checkbox are wrapped in `.unlock-input` so the existing 3-column
  `.unlock` grid still lays out correctly.
- `dashboard/styles.css` — appended `.unlock-input` / `.remember-row`.

**Default is unchanged** (`sessionStorage`). The checkbox is opt-in.
This was a deliberate user decision, not an oversight: the owner token is
scoped to the Worker submissions API only, unlike the old broad-scope
GitHub PAT this architecture replaced, so device persistence is a much
smaller exposure than it would have been pre-v29.

## Verification

Storage logic, driven in a real browser against the built pages
(`localhost:8899` static serve, then the live Pages deploy):

- checkbox **checked** → `{localStorage:"test-token-123", sessionStorage:null}`
- checkbox **unchecked** → `{localStorage:null, sessionStorage:"test-token-456"}`
- 「鎖定」button → both `null`, checkbox reset to `false`

Cross-page sharing (both pages are same-origin `hsintiger.github.io`, and
both use `TOKEN_KEY = "hsintiger_social_ops_owner_token"` — confirmed
identical on the live deploy):

- Wrote a value on `/news-radar/dashboard/`, navigated to
  `/news-radar/substack-submit/`, observed `lockState = "已驗證；已記住此裝置"`,
  submit button enabled, checkbox pre-checked.
- **Consequence for future agents:** unlocking once with "remember"
  checked unlocks the submit page *and* the dashboard. There is no
  per-page login. `meta-submit/` is only a `location.replace` redirect
  stub — it is not a third auth surface.

Live deploy confirmed serving the new build:

```
curl -s .../substack-submit/ | grep 'id="remember-device"'   → present
curl -s .../dashboard/app.js | grep 'localStorage.getItem'   → present
```

Incidentally verified: an invalid token in `localStorage` is
auto-cleared on dashboard load, because `load()` matches
`/credential|auth|unauthorized/i` on the 401 and calls `clearToken()`.
A stale/expired remembered token therefore self-heals into the
"paste again" state rather than wedging.

## Operational findings (not code changes — read these before debugging a stuck submission)

### Poller cron is configured every 5 min but GitHub actually runs it ~70 min apart

`.github/workflows/submission-poller.yml` declares `cron: "*/5 * * * *"`.
Observed reality on 2026-07-25:

```
13:39:27Z  →  14:49:24Z  →  15:56:03Z      (67–70 min gaps)
```

This is GitHub throttling scheduled workflows on public repos, not a
config bug. **A submission sitting in `queued` for an hour is expected
behavior, not a failure.** `gh workflow run submission-poller.yml` claims
it within ~12s if you need it now; the poller is idempotent (it claims
from a queue).

Also note `SUBMISSION_PROCESSOR_MODE` is now `live` (repo variable). It
was `paused` in earlier docs/memory — while paused, poller runs complete
with conclusion `skipped` and submissions accumulate untouched. If
submissions are stuck at `queued` and poller runs show `skipped`, check
this variable first.

### Only one launchd agent is loaded on the Mac

```
launchctl list | grep news-radar
→ com.hsin.news-radar.substack-fast     (loaded, StartInterval 300)
```

Present as plists in `~/Library/LaunchAgents/` but **not loaded**:
`com.hsin.news-radar.compose`, `.engagement`, `.snapshot`, plus the whole
legacy `com.newsradar.*` family.

This matters because Substack drafts are written **on the Mac**, not in
the cloud (Actions has no Claude/Gemini CLI subscription). A
`draft_priority` submission is served by the loaded `substack-fast`
agent. A plain `draft` (一般佇列) submission depends on the compose path
— **unverified this session whether anything services it.** Flagged, not
fixed; see "Out of scope" below.

### A short `clean_markdown` on a YouTube submission is NOT a failure — don't "fix" it

This cost time this session, so it is written down explicitly.

The cloud ingest stores only a **seed** for YouTube submissions. The
live test's row landed as:

```
fb87ad6f7006 | md_len=123 | word_count=10 | tags contain "immediate"
```

123 chars looks identical to the historical empty-shell rows
(`YouTube (no transcript)`, `md_len=96`, from 2026-07-03/07-08/07-14),
and it is tempting to conclude the cloud transcript fetch failed and
the draft will be garbage. **That conclusion is wrong.**

`scripts/drain_substack.py:_yt_seeds()` extracts YouTube URLs from the
`url` column plus any links in the body, and `_enrich()` then runs
`enrich_youtube_sources.py` on the Mac — Whisper transcription plus
written-report lookup — to build the deep material bundle that
`compose.py` actually consumes. Observed on the live test:

```
[drain] 20 user_substack item(s) (immediate only), 1 pending compose
  · fb87ad6f7006      10w  站在生成式語言模型現在的底層角度…  🎥yt
[drain] composing fb87ad6f7006 …
[drain] 🎥 1 個 YouTube 種子 → 建深度素材包（Whisper+書面報告，可能數分鐘）…
```

So the Mac's residential IP + local Whisper *is* the transcript path by
design; the cloud is not supposed to carry the transcript. The correct
health signal for a YouTube submission is the `🎥yt` tag and the
enrichment line in `/tmp/news-radar-substack-fast.out.log`, **not**
`length(clean_markdown)` in the DB.

(The old `md_len=96` rows titled literally `YouTube (no transcript)`
are a different, genuine failure — there the *title* itself records the
miss. Distinguish by title, not by length.)

## End-to-end trace of submission `79ce8554` (this session's live test)

| Stage | Observed |
|---|---|
| Frontend accept | `queued` at `16:23:17Z` |
| Poller claim (manually dispatched) | `dispatched` at `16:26:22Z` |
| Ingest workflow `30165630682` | `success`; `news_items` 30323 → 30324 |
| Worker status callback | `{"status": "source_queued", "updated_at": "16:27:21Z"}` |
| Mac drain claims it | `1 pending compose`, row `fb87ad6f7006`, flagged `🎥yt` |
| Whisper enrichment | started (`建深度素材包`), runs several minutes |
| `draft_created` | **still composing at time of writing** |

The status contract the frontend shows is honest — `source_queued` means
the material is in the DB, *not* that a draft exists. `draft_created`
only lands after the Mac agent composes.

Note on reading the drain log: several consecutive
`19 user_substack item(s) … 0 pending compose` lines *precede* the
successful pickup. Those are runs that fired before the cloud persisted
revision 52. The count going `19 → 20` with `1 pending` is the moment
the item actually arrived. Don't diagnose "0 pending" as a bug without
checking whether the Release revision had landed yet.

## Out of scope / parked

- **Unloaded launchd agents.** `compose`, `engagement`, `snapshot` have
  plists but are not loaded. Whether the 一般佇列 (`draft` mode, as
  opposed to `draft_priority`) path has any servicer on this machine is
  unverified. This is the highest-value next check — a user submitting
  with the default priority may get silent no-op. Canon install docs:
  `scripts/INSTALL_COMPOSE_LAUNCHAGENT.md`, health check:
  `scripts/mac_worker_doctor.py`.
- **Poller cadence.** If ~70 min latency is unacceptable for
  `draft_priority`, the fix is not the cron (GitHub ignores it) — it
  would need either a self-hosted runner or having the Mac agent poll the
  Worker directly instead of waiting on Actions.
- **Local DB is 112 MB.** Fine under the Release-based runtime state
  (2 GB/file limit) — this is no longer the 100 MB git-blob problem that
  broke the `state` branch in July. Noted so a future agent doesn't
  "fix" a non-problem.
