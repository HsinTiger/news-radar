### 2. `7843dde` — "記住此裝置" (remember this device) opt-in

Owner token was `sessionStorage`-only, so mobile Safari background

  `token()` now reads `localStorage` first then `sessionStorage`; new
  `storeToken(value, remember)` writes to exactly one store (clearing

**Default is unchanged** (`sessionStorage`). The checkbox is opt-in.
This was a deliberate user decision, not an oversight: the owner token is
scoped to the Worker submissions API only, unlike the old broad-scope
GitHub PAT this architecture replaced, so device persistence is a much
smaller exposure than it would have been pre-v29.

## Operational findings (not code changes — read these before debugging a stuck submission)

### Poller cron is configured every 5 min but GitHub actually runs it ~70 min apart

`.github/workflows/submission-poller.yml` declares `cron: "*/5 * * * *"`.
Observed reality on 2026-07-25:

```
13:39:27Z  →  14:49:24Z  →  15:56:03Z      (67–70 min gaps)
```

This is GitHub throttling scheduled workflows on public repos, not a
config bug. **A submission sitting in `queued` for an hour is expected
behavior, not a failure.** `gh workflow run submission-poller.yml` claims
it within ~12s if you need it now; the poller is idempotent (it claims
from a queue).

Also note `SUBMISSION_PROCESSOR_MODE` is now `live` (repo variable). It
was `paused` in earlier docs/memory — while paused, poller runs complete
with conclusion `skipped` and submissions accumulate untouched. If
submissions are stuck at `queued` and poller runs show `skipped`, check
this variable first.

### Only one launchd agent is loaded on the Mac

```
launchctl list | grep news-radar
→ com.hsin.news-radar.substack-fast     (loaded, StartInterval 300)
```

Present as plists in `~/Library/LaunchAgents/` but **not loaded**:
`com.hsin.news-radar.compose`, `.engagement`, `.snapshot`, plus the whole
legacy `com.newsradar.*` family.

This matters because Substack drafts are written **on the Mac**, not in
the cloud (Actions has no Claude/Gemini CLI subscription). A
`draft_priority` submission is served by the loaded `substack-fast`
agent. A plain `draft` (一般佇列) submission depends on the compose path
— **unverified this session whether anything services it.** Flagged, not
fixed; see "Out of scope" below.

### A short `clean_markdown` on a YouTube submission is NOT a failure — don't "fix" it

This cost time this session, so it is written down explicitly.

The cloud ingest stores only a **seed** for YouTube submissions. The
live test's row landed as:

```
fb87ad6f7006 | md_len=123 | word_count=10 | tags contain "immediate"
```

123 chars looks identical to the historical empty-shell rows
(`YouTube (no transcript)`, `md_len=96`, from 2026-07-03/07-08/07-14),
and it is tempting to conclude the cloud transcript fetch failed and
the draft will be garbage. **That conclusion is wrong.**

`scripts/drain_substack.py:_yt_seeds()` extracts YouTube URLs from the
`url` column plus any links in the body, and `_enrich()` then runs
`enrich_youtube_sources.py` on the Mac — Whisper transcription plus
written-report lookup — to build the deep material bundle that
`compose.py` actually consumes. Observed on the live test:

```
[drain] 20 user_substack item(s) (immediate only), 1 pending compose
  · fb87ad6f7006      10w  站在生成式語言模型現在的底層角度…  🎥yt
[drain] composing fb87ad6f7006 …
[drain] 🎥 1 個 YouTube 種子 → 建深度素材包（Whisper+書面報告，可能數分鐘）…
```

So the Mac's residential IP + local Whisper *is* the transcript path by
design; the cloud is not supposed to carry the transcript. The correct
health signal for a YouTube submission is the `🎥yt` tag and the
enrichment line in `/tmp/news-radar-substack-fast.out.log`, **not**
`length(clean_markdown)` in the DB.

(The old `md_len=96` rows titled literally `YouTube (no transcript)`
are a different, genuine failure — there the *title* itself records the
miss. Distinguish by title, not by length.)

The status contract the frontend shows is honest — `source_queued` means
the material is in the DB, *not* that a draft exists. `draft_created`
only lands after the Mac agent composes.

Note on reading the drain log: several consecutive
`19 user_substack item(s) … 0 pending compose` lines *precede* the
successful pickup. Those are runs that fired before the cloud persisted
revision 52. The count going `19 → 20` with `1 pending` is the moment
the item actually arrived. Don't diagnose "0 pending" as a bug without
checking whether the Release revision had landed yet.

## Later in the session — model swap, a real bug, and the KB framework layer

### `AGY_MODEL` switched to `Gemini 3.6 Flash (High)`

`.env` (gitignored, runtime-only) — was `Gemini 3.1 Pro (High)`.
`agy models` is the authoritative list; both the display form
(`Gemini 3.6 Flash (High)`) and the id form (`gemini-3.6-flash-high`)

so a typo fails loudly rather than silently falling back.

Note for whoever tunes this next: there is **no** `gemini-3.6-pro` in
the list. The choice is newer-generation Flash vs older-generation Pro,
not a straight upgrade. `Claude Opus 4.6 (Thinking)` is also available
and is the obvious next thing to A/B for long-form editorial work.

### ⚠️ Fixed: CJK transcripts were counted by whitespace (`d8b25f7`)

`scripts/enrich_youtube_sources.py` used `len(transcript.split())`.
Chinese has no inter-word spaces, so this undercounts massively.

Two impacts, the second one real:

1. Cosmetic: a 7,576-character Chinese transcript was labelled
   "814 字", which sent this session down a wrong diagnosis path
   (I wrongly concluded the composer was starved of source material).
2. **The same expression gated the Whisper fallback** — `< 80 tokens`
   meant "no subtitles, run ASR". A space-free Chinese caption track
   scores ~2, so its perfectly good subtitles would be **discarded** in
   favour of a slower, less accurate ASR run.

Fixed with `_content_len()` (CJK codepoints counted individually,
whitespace tokens elsewhere). Verified: zh-with-spaces 818→7669,
zh-without-spaces **2→7666** (the misfire case), English 6008→6136
(no regression), placeholder `(no transcript)` still scores 3 so the
Whisper trigger still fires correctly.

### YouTube extraction: agy/Gemini reads video natively, and accurately

Tested because the current no-caption fallback is `faster-whisper`
model **`base`**, which is weak for Chinese.

`agy --model "Gemini 3.6 Flash (High)"` given a bare YouTube URL
answered three questions that are **only** answerable from that

Recommended stack (not yet implemented):


Deliberately **not** recommending Gemini over the captions API when
captions exist: captions are ground truth, an LLM is a model output,
and this system's contract is verifiable sourcing.

Two corrections to things I initially got wrong, so nobody repeats them:

**What is actually broken:** `market-universe.yml` (`Hourly cross-asset
market universe`) fails every run, which in turn leaves
`Deploy dashboard + Quartz wiki` permanently `skipped`. The failing step
is `Bind verifier to current market artifact`, exiting on
`Verifier hard failure blocks hourly market publication` — i.e.
`verify_daily_data.py` returned `status: fail`. That is the fail-closed
contract working as designed, not the bug.

Reproduced locally: `{"status": "fail", "failures": 42}`. After running
`collect_market_universe.py` from a residential IP the count only drops
to **36**, so staleness/IP explains at most 6 of them. The residue is a
**timestamp contract break** between collector and verifier:

```
market universe date mismatch: 2026-07-25 != 2026-07-24
BTC Binance USDT/USD 匯率逾時或時間未知
BTC Coinbase 現貨來源時間未知
ETH OKX USDT/USD 匯率逾時或時間未知
```

Sources return data with **no readable timestamp**, so the verifier
cannot prove freshness and correctly fails closed. Likely an upstream
API response-shape change, or the collector no longer capturing the
timestamp field. That is where to dig — not at the verifier.

Note `collect_market_universe.py` itself self-reports
`quality: "fail", sources: 74, execution_errors: 0` — it fetches fine
and knows its own output is bad. Fixing the timestamp capture should
clear both.

### 4. ⚠️ Whisper was transcribing every video as English (`87c9635`)

**The most consequential find of the session.** `_whisper_transcript`
passed `language="en"` unconditionally. Same video, same model, only that
argument changed:

```
language="en"  →   261 Chinese characters
language=None  → 9,231 Chinese characters
```

This explains the strange source bundle from earlier today. It was never
an English video — we were transcribing a Chinese one into English.
**Any Substack draft built from a no-caption Chinese video before this
commit was written from a corrupt transcript**, which is worth
considering before trusting those drafts.

Also added an agy/Gemini lane between captions and Whisper, with its
boundary established by test rather than assumption: it reads the
**caption track, not the audio** (verbatim match on a captioned video;
"無法讀取影片" on a caption-less one). It therefore cannot replace Whisper
for the case that actually needs a fallback, and is documented as a
resilience path for caption-fetch failure only. `--no-agy` skips it.
