## 2. 關鍵發現 / 決策

### 2.1 三層相互糾纏的 bug：表象 vs 真相

**最初表象**：IG 互動數字全 0、FB 數字全 0、Threads 部分數字 OK。

**剝洋蔥順序**（每一層都以為「應該是這個」、繼續挖才發現底下還有）：

1. **第一層（IG fetch bug）**：`fetch_ig_insights` 只打 `/{post_id}?fields=like_count,comments_count`，沒打 `/{post_id}/insights?metric=...` endpoint，所以 reach / saved / views 永遠 hardcode 為 0。修法：加 insights 端點呼叫，metrics 用 v22+ 相容的 `reach,saved,views,total_interactions`（**不能再用 `impressions`，v22 deprecated**）。

2. **第二層（FB post_id 格式）**：`fetch_fb_insights` 對某些 post_id 回 `(#100) Tried accessing nonexisting field (reactions)`。原因是 publisher 在不同路徑寫 DB 的 `platform_post_id` 不一致——/photos with `url=` 寫裸 `{post_id}`，/photos with file 寫完整 `{page_id}_{post_id}`。Meta Graph API 對裸 post_id 連 reactions.summary 都不開。**Defensive 修法**：`_normalize_fb_post_id()` 看到沒底線的 ID 就主動加 `{FB_PAGE_ID}_` 前綴。

3. **第三層（Threads native column 從來沒被填過）**：schema 早就有 `replies` / `reposts` / `quotes` 三個欄位，但 `fetch_threads_insights` 把 Threads API 的 replies alias 成 `comments`、把 reposts+quotes 合併成 `shares`，那三個 native column 一直是 schema 預設 0。dashboard 因此抓不到 native 訊號。修法：寫 native 欄位、把 comments/shares 對 Threads 留 0（這兩個概念對 Threads 不存在；不偽造）。

4. **第四層（沒人 commit）**：Engagement script 跑完印 `OK=50 Fail=0`，DB row 卻沒變多。**根因**：Python 3.6+ 的 sqlite3 在 `conn.close()` 不再隱式 commit，`sync_all_posts` 跟 `__main__` 都沒呼叫 `commit()`，整批 INSERT 被 rollback。修法：`sync_all_posts` 結束 return 之前 `conn.commit()`。

5. **第五層（worker 從來沒排程）**：上面這些修完之後發現 DB 紀錄 stale 11 小時。grep 整個 codebase 沒人呼叫 `src.engagement`——`launchd` 沒 plist、`compose_hourly.sh` 沒 hook、production 從來沒在跑。修法：寫 `scripts/com.hsin.news-radar.engagement.plist` + `scripts/news_radar_engagement.sh`，每 4 小時跑一次。

### 2.2 FB 「貼文跑去相片區」的真相：App 在 Dev Mode

User 透過朋友 / 匿名 Safari 視角發現所有 pipeline 發的文都不在 Posts tab。我**錯誤地**診斷為「/photos endpoint 結構性歸到 Photos tab」，提了兩條替代方案：

1. **第一次（link share 模式）**：改 `/feed?link=...&message=...`，讓 FB 自動抓 link card。User 反推「但我們很多是原創觀點不是新聞轉發」，**對的反推**——抽 case 取消。

2. **第二次（attached_media 模式）**：改成 Step 1 `/photos?published=false`、Step 2 `/feed?attached_media=...`。寫了完整 code、加了 `FB_FALLBACK_PHOTO_ID` env var、修了相對路徑 og_image、跑驗證。

3. **真相揭曉**：User 在 Meta Developer Dashboard 看到 **「應用程式模式：開發中」**，按了上線。**所有歷史 `/photos` 上傳的貼文 retroactively 出現在 Posts tab**。Posts vs Photos 從來不是 endpoint 分類問題，是 App permission state。

### 2.3 Lesson：先檢查 fundamentals 再重設計架構

我花了 ~90 分鐘在 publisher endpoint 改寫，本來只要先讓 user 截圖 Meta Developer Dashboard 就會看到 Dev mode 那個 toggle。

**未來判斷規則**（給下次 Claude）：
- 出現「API call 200 OK 但效果隱形」→ 先查 app mode、permission scope、token type
- 出現「owner 看得到但 visitor 看不到」→ 跟上一條同。**不是先改 endpoint**
- 出現「公開 vs admin 視角差異」→ 先想 publisher state，再想 architecture

### 2.4 Endpoint 改寫 → revert 的取捨

attached_media 兩步流程**也有效**，但 Live mode 解決可見性後，/photos 一步流程：

- API call 少 1 次（~1 秒省下）
- FB 對 photo post 有 algorithm reach 紅利
- Photos tab + Posts tab 雙重曝光（attached_media 主要在 Posts tab）

沒有保留兩步流程的理由。Revert，但**保留 `_is_valid_http_url` URL guard**（這個是 attached_media 那次踩到爛 og_image 之後加的，現在 /photos 也用得上）。

### 5.5 哪些東西這 session 出過 surprises

- Python 3.6+ sqlite3 不再隱式 commit on close — **所有 batch 寫入都要記得 commit()**
- Meta Graph API v22 把 IG `impressions` 改成 `views` — **不能寫 impressions 否則 #100**
- FB `/{post_id}?fields=...,shares` 的 `shares` 子物件被砍 — **要走 `/insights?metric=...` endpoint**
- FB `/photos` 不同 path 寫的 platform_post_id 格式不一致——defensive 用 `_normalize_fb_post_id()`
- Meta App「開發中」mode 跟「上線」是兩個世界，**Dev mode 下所有 public visibility test 都失準**

## 6. 值得回看這 session 的地方

1. **Engagement 那條鏈拆五層**：每一層修完都以為「應該完成了」、跑驗證才發現底下還有。連續五個 root cause 互相 mask，這個 pattern 很值得記下來。

2. **endpoint 改寫 → revert 看似浪費，其實留下兩個有用副產品**：
   - `_is_valid_http_url` URL guard（在 /photos 也用得上）
   - `cleaner.py::extract_og_image(base_url=...)` urljoin 修正（解決相對路徑爛 URL）
   這條經驗：**寫死的 architecture 改寫常常會在過程中順手修一些 latent bugs**，不要因為 main goal revert 就把支線 fix 也丟掉。

3. **「先檢查 fundamentals」這個經驗對下次 Claude 最有價值**：
   - 我跟 user 從「為什麼 FB 公開看不到」進去
   - 我直接跳到「endpoint 選錯」+「重新設計 publisher」
   - 拖了 90 分鐘才找到 App Dev mode toggle
   - 如果第一個 prompt 就讓 user 截 Meta Developer Dashboard 整頁，10 分鐘就能找到根因
   
   未來規則：**「API success 但效果隱形」→ 先查 permission state**

4. **三個 agent 的協作模式**（這次有 Gemini Review、Dashboard Agent、Backend Agent 三條）：
   - Gemini 提的 attached_media 想法是對的方向
   - 我的 attached_media 實作對的，只是 root cause 不在這裡
   - Dashboard agent 同步 ship Q2、等 Q1
   - 這種「平行 ship、不互相等」的協作有效率，但**root cause 沒抓對的時候，所有 agent 的工都會跟著走偏**
